# Техническая архитектура

Статус: рабочая основа. Решение: [ADR 0001](adr/0001-foundation.md).

## Границы

```mermaid
flowchart TD
  UI[Flutter: каталог и игровые экраны] --> Controller[Контроллер сессии]
  Controller --> Local[LocalSessionAdapter]
  Local --> Core[Чистый Dart game_core]
  Local --> Content[Встроенные JSON-наборы]
  Controller -. будущий онлайн .-> Remote[RemoteSessionAdapter]
  Remote -. HTTPS / Socket.IO .-> Server[NestJS: команды и персональные проекции]
  Server -.-> DB[(PostgreSQL)]
```

Сплошные связи — направление локальной реализации; пунктир — дальнейший этап.
LocalSessionAdapter и SpyController подключены к локальному игровому сценарию.
Адаптер выбирает локацию из неизменяемого набора фиксированной версии; контроллер
хранит сессию ядра и состояние показа карточки и доступности приложения.
Flutter-экран передаёт lifecycle и запускает обновления таймера, часы внедряются
в контроллер. Повтор партии сохраняет настройки в памяти.

## Мобильное приложение

Flutter отвечает за Android/iOS, Material-тему и адаптивные экраны. `game_core`
не импортирует Flutter. UI вызывает команды ядра и рисует состояние; таймер не
уменьшает сохранённый счётчик каждую секунду, а вычисляет остаток по deadline.
Время передаётся ядру аргументом, чтобы фон/возврат и тесты не зависели от виджетов.

На старте достаточно небольших контроллеров на стандартных средствах Flutter.
Riverpod/GoRouter/Drift из беседы разумны при появлении асинхронной сессии, маршрутов
и persistence. Не подключаем Freezed и генераторы ради двух моделей.
Подход к разделению UI/data согласован с [рекомендациями Flutter](https://docs.flutter.dev/app-architecture/guide).

Секретный экран скрывается при inactive/paused и после явной передачи телефона.
Возврат из фона ведёт на закрытую карточку. Это UX-барьер: владелец одного телефона
технически контролирует всё локальное состояние; нельзя обещать криптографическую
изоляцию участников на общем устройстве.

## Правила и переиспользование

Первый модуль — «Шпион». Общее ядро минимально: игрок, фазы, выдача ролей,
закрытый результат и публичная проекция. Каждая игра может иметь собственный FSM;
не заставляем «Крокодила» и социальную дедукцию использовать одинаковые фазы.

В Dart и TypeScript правила выполняются отдельно. Общие вещи — JSON-схемы,
описание правил и затем JSON-векторы действий/ожидаемых состояний для обеих реализаций.
Для онлайн-версии серверные правила авторитетны. Клиент может показывать прогноз,
но не решает победу, роли, дедлайн или допустимость голосования.

## Сервер

Модульный монолит NestJS. Сейчас только `/health`, независимый от БД. Затем:
rooms, sessions, games/spy, content; покупки и аккаунты по реальной потребности.
Гость получает непрозрачный player token; PIN — способ найти комнату, не авторизация.
Секреты возвращаются только в личной проекции после проверки членства.

PostgreSQL добавляется вместе с комнатами и транзакционными изменениями состояния.
В транзакции: проверка версии → применение команды → новое состояние → сохранение
результата `commandId`. Рассылка после commit; при обрыве клиент запрашивает snapshot.
Отдельный event sourcing, Redis, брокер и микросервисы сейчас не нужны.

Socket.IO сохраняет порядок доставленных сообщений, но по умолчанию не гарантирует
повторную доставку. Поэтому ack, дедупликация и resync — наша ответственность:
[delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/).

## Контент и контракты

JSON-схема draft-07 с `schemaVersion`, `gameId`, `version`, `locale` и устойчивыми ID.
Версия набора фиксируется в партии, чтобы обновление не меняло активный раунд.
Встроенный JSON — первый источник; скачивание и store entitlement добавляются позже.
REST описываем OpenAPI при реализации API; realtime payload — отдельные JSON-схемы.
OpenAPI сам по себе не описывает весь двусторонний Socket.IO-протокол.

## Сборки и данные

Локальный режим работает без сервера. Первое сохранение — настройки и имена;
восстановление секретного активного раунда проектируется отдельно, без записи ролей
в открытые логи. Перед аналитикой определяем события, согласие и retention.

CI сейчас проверяет поведение и статический анализ. Подписанные Android/iOS-сборки,
миграции, rollout и store-публикация появятся после выбора app ID и аккаунтов.
iOS-сборка требует macOS/Xcode; локальная Linux-проверка Dart/Flutter её не заменяет.
